# Harris 美髮 LINE 客服：第一版設計提案

狀態：待使用者審閱；尚未建立程式、部署服務或連接正式 LINE。

建置前檢查：獨立審閱者已閱讀本提案，未提出會阻擋撰寫實作計畫的重要問題。外部帳號與預約平台串接仍須實際驗證。

## 目的與已知需求

使用者是美髮髮型師，曾經營 Reels，希望客人傳訊息到官方 LINE 時，系統能先依他的語氣回答，再回報客人需求及他應處理的事項。程式部署在雲端，個人電腦關機仍能提供服務；回覆有問題時，可以持續修正。後續才擴充為統整腳本、剪輯及營運工作的助手。

使用者已選擇「撰寫程式並部署到雲端」，而非以無程式碼流程工具為主。

目前儲存庫沒有提交與專案檔案；官方 LINE 的串接狀態、雲端帳號及 AI API 存取尚未確認。現有 ChatGPT 訂閱不能視為已具備 API 額度。

使用者提供的網址：

- 個人網站：https://harrishair.tw/
- 公司預約系統：https://g7.zoom-world.tw/Round2HairSalon/index.aspx

本次經既有網路代理讀取兩個網址均遇到 CONNECT 403，尚未讀取頁面內容，不能據此判定網站離線、供應商名稱或有無 API。兩個網域已加入環境設定草稿，尚未套用或發布。

## 方案比較與選擇

1. 自訂小型雲端程式：可控制回覆依據、對話狀態、人工接手及版本變更；需要測試、部署及維護。使用者選擇此方向。
2. Make／n8n 等流程工具：適合簡單串接，但例外處理、持久化對話狀態與複雜分支仍需要維護；未選用。

## 建置者提出的具體工具選擇

下列是建置者的建議，尚非使用者已確認的工具採購或部署授權細節：

- Node.js LTS、TypeScript、輕量 HTTP 框架及官方 API SDK；確切套件與受支援版本在實作計畫中確認並鎖定。
- LINE Messaging API 接收訊息、回覆客人及發送管理通知。
- OpenAI API 產生受店務規則約束的回覆與結構化需求摘要；模型以可設定方式選擇，不綁死未核實的型號。
- Render 的常駐 Web Service 與持久化 PostgreSQL，讓應用與資料庫在同一平台管理。正式版選擇符合持續服務與備份需求的方案，不依賴會休眠的免費服務。
- GitHub 保存程式、非個資的店務指南及回覆規則，每次修改可測試、審閱及回復。
- 第一版由單一常駐應用同時執行 HTTP 接收與資料庫工作佇列，不增加 Redis 或多代理框架。

## 第一版範圍

- 接收文字訊息，依已確認的服務、價格、地址、營業時間及預約規則回答。
- 以使用者提供並去識別化的問答範例整理語氣規則；避免把客人個資放進 GitHub。
- 保存必要對話狀態，整理預約需求、詢問項目及待辦，回報店主。
- 引導至既有公司預約系統；個人網站可作為資訊入口，實際連結用途待頁面驗證。
- 支援人工接手、恢復自動回覆及回覆問題的回饋紀錄。
- 能在雲端重啟後恢復待辦與處理狀態。

暫不包含：自動登入公司系統、模擬點擊建立預約、付款、全量匯入 LINE 歷史訊息、照片髮況判讀、管理網站、剪輯助手或「部長」自動分派工作。LINE 歷史紀錄不假設能由 Messaging API 取得。

## 預約與回覆邊界

至少區分三種狀態：

1. **預約需求**：客人說想預約；記錄期望日期、時段、項目及原始表述，仍待確認。
2. **客人自述已預約**：客人說已在平台完成；系統尚未向平台核實。
3. **平台已確認**：只有從受支援且驗證來源的 API／webhook，或店主明確確認後，才能標記成功；同時記錄確認來源。

第一版尚無平台串接時，不宣稱查到空檔、建立成功或取得平台訂單。將客人的「明天下午」保留為需求，不憑空產生精確時間。對話中相對日期依訊息時間及 Asia/Taipei 換算，不確定時詢問。資料庫以 UTC 儲存時間，通知以台灣時間呈現。

複雜染燙、染黑後漂髮、需要看髮況的問題、未提供的確切報價、客訴、退款與特殊承諾交由本人處理。圖片、音訊或不支援的訊息類型給予簡短說明並建立待辦，不假裝已判讀內容。

## 一次客人訊息的處理流程

1. 保留原始請求內容，先驗證 LINE 簽章，再解析事件；無效簽章不進入 AI 或通知流程。
2. 將事件以 LINE 事件識別碼去重，持久化寫入事件及工作；寫入成功才回 HTTP 200。空事件的 webhook 驗證請求也能正常回應。資料庫寫入失敗回可重試的錯誤。
3. 背景工作立即處理，檢查測試帳號限制、店主管理訊息及人工接手狀態。
4. 從已審閱的店務指南與必要的近期對話取得上下文，呼叫 AI 產生回覆草稿與結構化摘要。
5. 由程式驗證回覆與摘要：不准模型指定通知對象、修改權限、執行任意工具或自行將預約改成成功；未知內容進入澄清或人工處理。
6. 在 LINE 回覆憑證的有效限制內嘗試回覆。設定整體處理期限，AI 超時／失敗時使用簡短的人工確認提示，仍建立待辦。
7. 先保存回覆結果與待辦，再由持久化通知工作回報店主。通知失敗不重新執行 AI 或重複回覆客人。

LINE 回覆憑證依官方限制視為短效且一次性使用；實作前核對官方文件。不對過期工作無限重試，也不在回覆結果未知時盲目改用推播重發。將送達狀態區分為成功、失敗、未知，讓店主能辨識。

工作佇列用資料庫租約、有限重試及失敗狀態避免程序重啟後遺失工作；重複事件不產生第二次客人回覆或第二個待辦。外部傳送在網路中斷時無法保證完全一次，必須保留未知狀態，不能以資料庫去重宣稱消除此風險。

## 店主通知與人工處理

建議使用店主自己的個人 LINE 接收同一官方帳號的管理通知；店主需先加好友，且帳號能接收官方帳號訊息。通知對象由後台設定的唯一管理員 LINE user ID 決定，不能用「第一個傳註冊的人」或客人傳入的欄位取得管理權限。

每則客人訊息完成初步處理後產生一份摘要，目標在一分鐘內送出，依外部服務實際延遲而定；無法送達時保存狀態及待辦，不能宣稱已通知。通知包含：

- 客人代號／必要顯示名稱、訊息收到時間。
- 詢問內容、機器人回覆摘要與送達狀態。
- 期望預約時間及項目；缺漏處標示待詢問。
- 預約需求／客人自述／已確認的明確狀態。
- 是否需要店主處理、待辦編號與建議下一步。

範例：

> 14:32 收到 C001 訊息：希望週五下午剪髮。
>
> 已提供預約連結；確切時間待確認，尚未確認預約成功。
>
> 待辦 T001：請確認客人是否仍需協助預約。

每則通知會使用 LINE 訊息額度，正式使用前確認帳號方案。超額或被封鎖等失敗記錄在資料庫及不含對話內文的操作日誌中。

店主專用指令提供：查看待辦、接手指定客人、恢復自動回覆、完成待辦及記錄某次回覆的問題。具體語法由建置者決定並附中文說明。店主訊息不送入客人客服流程、不為自己產生通知。

客人要求真人或系統判定需人工處理時，切換至人工狀態並通知店主。店主從 LINE 官方帳號後台主動處理前，也可先發接手指令；不假設程式能偵測所有由後台手動發出的訊息。人工狀態下保存新訊息並通知店主，不自動回答；待店主明確恢復。

## 持續修正方式

- 店主提供問題回覆的待辦／事件編號與正確回法；回饋先保存在私人資料庫。
- 與使用者確認後，將可泛用的修正整理進店務指南、語氣範例或程式規則，移除個資再納入版本控制。
- 為具體錯誤加入有意義的回歸案例，驗證後部署；保留版本識別，可回復上一版。
- 不把客人訊息或未審閱的回饋直接當成永久規則，不承諾模型會自行持續學習。

## 最小資料與安全設定

資料包括事件識別碼／時間、必要客人識別碼、對話狀態、必要文字、抽取的需求、回覆送達狀態、待辦、通知工作及店主回饋。用資料庫限制維持關聯與去重；保留執行版本供追查。

預設提案：原始對話與包含原文的回饋保留 30 天；通知載荷及其他包含對話原文的欄位遵守同一期限。已結案待辦的精簡資料與事件去重識別碼保留 90 天；未結案待辦保留到結案後再按期限清理。尚未處理的原文到期先標記提醒、移除超期原文，保留處理所需的最少狀態；更長期限需另行決定。平台備份的保留期另行記錄，不能宣稱刪除資料庫資料就立即刪除所有備份。

連線保持 TLS 驗證；管理員 ID、LINE 憑證、AI API 金鑰及資料庫連線設定放在部署平台的環境設定，不提交至 GitHub，不在聊天室提供值。日誌排除憑證、完整訊息及完整請求內容。AI 僅接收處理當次問題所需的資料。正式使用前確認店家對對話資料處理的告知方式。

資料庫使用受支援的備份方案；部署時執行版本化 migration，實作中不以清空資料庫作為升級方式。

## 分階段設定與驗收

1. **連線測試**：取得官方帳號管理權限、啟用 Messaging API、安全設定憑證，部署 HTTPS webhook；先限制可回覆的測試 user ID，回固定測試文字。測試訊息若未在允許名單中，不送 AI、不回覆、不建立私人通知內容；既有正式客服方式持續承接。
2. **AI 與店務知識**：加入經使用者確認的基本店務資料、語氣範例及現有預約連結。缺漏資料不得捏造。
3. **店主回報**：設定管理員 ID，確認實際收到含時間、項目、狀態及待辦的通知；測試接手、恢復及回饋。
4. **可靠性驗證**：確認無效簽章遭拒、相同事件不重複處理、空 webhook 驗證正常；AI／LINE 失敗能記錄及交接；程序重啟後待辦與人工狀態保留。用模擬服務測故障，以真實 LINE／AI 測試帳號驗證至少一輪完整流程。
5. **正式啟用**：確認服務持續運作方案、資料保存、LINE 既有自動回覆設定及回復舊流程的方法；通過測試後再解除客人限制。部署完成與測試通過分別報告，沒有真實憑證時只報本地與模擬驗證結果。

不會在本設計審閱階段傳送 LINE 訊息、建立公司預約、建立付費資源或推送 GitHub。

## 外部前置與可獨立進行的工作

- 待使用者確認本提案後，可先建立程式、假資料測試與部署檔，不需提供所有歷史訊息。
- 真實串接需要：LINE 官方帳號管理權限與安全憑證、可用 AI API、雲端平台帳號與方案、可用的 GitHub 遠端提交及部署連結方式、店主通知 ID 與基本店務資訊。逐項以安全設定方式處理，不在聊天要求密鑰。
- 公司預約平台是否提供 API／webhook／其他受支援的通知與權限仍未知。先檢查公開資訊；如無公開資訊，詢問供應商。這是自動確認平台預約的前置，不阻擋第一版的回覆、需求整理及連結引導。
- 網路設定草稿僅新增 harrishair.tw 與 g7.zoom-world.tw；其他必要 API 目的地於實際串接時依現有政策增補，不能繞過代理或關閉 TLS。
- 日後的「部長」可沿用版本化知識與待辦，但須另行設計權限與工具介面；不假設能直接控制既有 ChatGPT 專案或所有工具。
