# 有界自然對話與已核准報價

## 目的與範圍

本人已同意先實作再看範例，確認後才更新線上。基準401bf62；本輪僅本地程式、mock測試、文件與提交，不推送、不部署、不呼叫真API或LINE、不改live/ai、憑證或付費服務。不做網站/POS同步或選單字詞免AI捷徑。

現況：AI讀到history，但applyPolicy把reply幾乎全換成固定段落；因此「我是新客」無法接續報價，預約總是重貼連結。history已有每客人隔離、30天／10turn上限與持久events，無需新記憶服務。首次AI身份另在session保存，保持原樣。

## 方案與取捨（本次實作判斷）

1. 再增模板分支：便宜但不能達成改變說法與順序，不採。
2. 直接發模型自由文字：可自然，但無法可靠鎖住金額與預約承諾，不採。
3. 採用有界生成：從客人原文整理服務／長度／身分與本則時段，先建立本次可用事實及缺項；同一個AI呼叫產生短回覆，敏感事實使用程式給的具名placeholder，程式驗證後填入核准內容。AI可組合已審閱正向口語片語並改變順序，不再每次覆寫整段模板。不合格結果降級為本則安全簡答；API失敗仍交Harris。

自然程度與安全的取捨：模型不能自由改寫金額、日期是否營業或已完成外部操作；這些使用核准片段。審查發現只禁敏感詞仍可用「敲定囉」「老闆收到囉」「才怪」改變含意，故不再採無界自由銜接加黑名單，而使用同一份有限正向片語清單供prompt與guard共用。片語可組合／換序，實質內容依上下文事實改變；未審閱語句一律降級。逐個literal fragment驗證，不跨placeholder拼字；每則最多一個核准友善😊。這是有界的自然對話改善，不是任意自由聊天，也不把驗證當成任意自然語言的形式證明。沒有真API授權，本輪不宣稱真模型品質、草稿通過率或滿意度已驗收。

## 人工接手與事件邊界

沿用既有規則：任何明確預約requested都needsHuman=true，首次回覆後即sticky handoff，不因自然對話擅自解除。例「胸上染髮多少→我是新客→週六兩點呢」可自動接續，最後回Harris待確認並接手；其後「三點也可以」只整理／通知店主、不再自動回客人。若開頭已說想預約，亦可能先詢問缺項就轉人工；這是本輪刻意保留的界線。

handoff後仍從本則原文取新時段（不把上則時段當本則更新），可延續服務，保留owner決定、通知獨立迴圈、去重、lease、送出失敗處理及首次AI介紹。不得說已通知／備註，因AI生成時尚無該外部送達證據。無新增migration或環境變數。
