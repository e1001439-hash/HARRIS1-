## 1. 先試用本機 demo

安裝 Node.js 24 LTS（版本記在 `.node-version`），開啟終端機並切到專案根目錄：

```bash
npm ci
npm run check
npm test
npm run build
npm run demo
```

最後一個指令會持續執行。Demo 使用內嵌 PostgreSQL 與假的外部服務，不需要 LINE 或 AI 金鑰。預設連接埠為 3000，資料保存在 `.local/demo`，模擬送出的訊息保存在 `.local/demo-outbound.jsonl`；兩者都不應加入 Git。這些本機模擬輸出只能用假客人資料測試。

在第二個終端機切到同一目錄，送一則已簽章的假訊息：

```bash
npm run demo:send -- "我想預約剪髮，週五下午方便嗎？"
```

檢查模擬輸出有客人回覆及店主通知，預約仍為需求、沒有宣稱預約成功。按 `Ctrl+C` 停止 demo，再執行 `npm run demo`，確認資料保留；不要刪除資料目錄來模擬重啟。

可在同一台機器內檢查健康狀態。以下是終端機驗證，不是可分享的預覽網址：

```bash
curl --fail http://127.0.0.1:3000/healthz
curl --fail http://127.0.0.1:3000/readyz
```

Demo 的成功只證明本機流程；真實 LINE、AI、資料庫 TLS 與 Render 設定仍需後面的真人測試。

## 2. 準備安全的環境設定

初次啟動沿用既有 LINE 官方帳號及 Messaging API channel、店主個人 LINE 與持久化 PostgreSQL。先保留 `BOT_MODE=test`（只開放測試名單）與 `RESPONSE_MODE=fixed`（固定回覆），安全填入下表四個必填欄位即可，不必先知道測試者 ID，也不需要 AI 金鑰或模型。指定的另一位測試者可等真實測試取得授權後，再由店主配對並確認加入。AI 模式才另外需要可用的 OpenAI API 帳號、金鑰與已確認可用的模型。

本機可以複製 `.env.example` 為 `.env` 再自行填入；程式會載入該檔案，已由執行環境提供的值優先。Render 則在服務的環境設定中輸入，不上傳 `.env`。`.env.example` 只有空欄與安全預設，不能直接當成正式設定使用。

請勿在聊天、GitHub issue、程式碼或截圖中提供密鑰、配對碼、token 或含憑證的連線網址；也不要把整份環境變數或資料庫連線字串貼進日誌。配對文字只在店主與指定測試者之間私下傳遞。若曾外洩，先在來源平台撤銷／重發，再更新部署環境。

## 4. 在 Render 準備持久化服務

本專案建議一個付費常駐 Web Service 加一個付費持久化 PostgreSQL，放在相同區域。免費休眠服務不適合作為此正式客服流程。Render、LINE 訊息額度與 OpenAI API 分別計費，請以當時官方方案為準，不以本文件估算固定月費。

本人此次新建頁最後選擇 **US$0／月的免費 Web Service** 並自行嘗試部署；這不代表資料庫或其他用量免費。程式沒有付費方案檢查，不能僅憑啟動失敗就認定必須升級方案。已有 Available 的 `harris-line-db`，不要因此再建立另一個資料庫。以下順序供後續授權與驗收時參考：

1. 先經本人授權，在 GUI 確認費率與服務設定，並關閉自動部署。
2. 目前 GitHub `main` 已有通過 CI 的 `3a375bb`；診斷版已由本人部署。本輪後續通知模擬驗收的新增內容先留在本地，不進行新推送／部署。
3. 由本人安全填入四個必填欄位與下表常數；Root Directory 留空，使用儲存庫根目錄。
4. 完成資料庫 TLS 與 migration，確認 Web Service `/readyz` 成功。
5. LINE Verify 通過後，店主先測 `/help`，再依第 5 節開啟配對。
6. 店主親自核對指定測試者後明確確認，再測一則一般訊息的固定回覆、店主通知、人工接手及重啟保留。

`render.yaml` 只描述 Web Service，沒有資料庫方案代碼或自動建立資料庫的設定。本次讀取 Render 官方方案／Blueprint 文件遭雲端網路代理拒絕，無法核對目前 PostgreSQL 方案代碼；請在 Dashboard 依當時官方資訊選擇付費、持久化且符合備份需求的方案。請勿把「檔案已備妥」理解為已建立或付款。

1. 確認要部署的 GitHub 儲存庫與分支，先通過 CI，再由有權限的人連接 Render。
2. 沿用既有 `harris-line-db`，記下區域、支援版本、備份／時間點還原功能及保留期；完成一次還原測試後才存放正式客人資料。
3. 在相同區域建立 Node Web Service。可手動輸入下表，或審閱後套用儲存庫的 Blueprint。Blueprint 使用付費 `starter` Web Service，但未預選區域；套用前，必須先在 `render.yaml` 的該 service 新增與資料庫完全相同的 `region`，代碼從當時 Render 官方資訊核對。若無法確認代碼，改用 Dashboard 手動建立並選擇相同區域，避免平台預設到別區。開始建立前核對當時方案及帳單。
4. 選用支援 TLS 且可驗證憑證與主機名稱的 PostgreSQL 端點，將其連線字串安全填入 Web Service 的 `DATABASE_URL`。本次先用 External Database URL 的完整網域；Internal 短主機名是否符合憑證尚未核實，同區域不代表驗證一定相容。網址可不帶 SSL 參數；若含 `sslmode`，程式只接受 `verify-full`，會拒絕 `require` 等其他值。不要把連線字串放進 Git 或聊天。
5. 補齊資料庫、LINE 簽章密鑰、LINE 發訊憑證與店主識別碼四個安全欄位。保留 `BOT_MODE=test`、`RESPONSE_MODE=fixed`。Blueprint 中僅這四欄為 `sync: false`，由本人安全提供；不要求預先填入測試者 ID 或 AI 金鑰／模型，店務兩個檔案已隨儲存庫附上。

| Render 欄位 | 設定 |
| --- | --- |
| Runtime | Node，使用 `.node-version` 的 24 LTS |
| Root Directory | 留空，使用儲存庫根目錄 |
| Build command | `npm ci --include=dev && npm run build` |
| Pre-deploy command | `npm run migrate` |
| Start command | `npm start` |
| Health check path | `/readyz` |
| 自動部署 | 初期關閉；驗收後再決定是否開啟 |

`npm run migrate` 執行編譯後的 `dist/migrate.js`，因此 build 必須先完成；`npm start` 執行 `dist/main.js`，也會在監聽連接埠前自動執行 migration，所以手動服務的 Pre-deploy 留空不等於漏做更新。Migration 是版本化資料更新，不是清空重建資料庫。不要在每次部署時刪表、刪資料庫或重設客人狀態。

正式資料庫連線必須啟用 TLS 並驗證憑證與主機名稱，internal URL 本身不保證這些條件。依供應商目前的連線要求選擇支援驗證的端點，必要時使用外部端點；若出現憑證錯誤，檢查主機名稱、CA 信任與官方連線方式。請勿設定 `rejectUnauthorized: false`、停用 TLS 驗證或把正式資料搬到本機 demo 來繞過問題。尚未驗證真實資料庫連線前，不視為正式設定完成。

部署後先確認 `/healthz`（程式存活）及 `/readyz`（資料庫可用）均成功；只有存活不代表資料庫正常。此時仍在測試模式，尚未正式開放客人。

## 5. 驗證 webhook、配對與固定回覆

以下真實發訊與配對需另經本人授權。服務完成資料庫 TLS／就緒檢查後，再依序操作：

1. 從 Render 取得服務的正式 HTTPS 網域。在 LINE Developers 的 Webhook URL（LINE 接收訊息的入口）填入該網域加上 `/webhook`，例如 `https://你的服務網域/webhook`。
2. 使用 LINE 的 Verify 功能。程式支援已簽章、`events: []` 的空驗證請求；成功只證明此項檢查，不代表客人回覆或店主通知已通過。
3. 啟用 webhook，並確認 LINE 的 webhook 重送設定符合需求。程式先驗證原始內容簽章，再把事件與工作寫入資料庫，成功持久化後才回 HTTP 200。
4. 店主以個人 LINE 對官方帳號傳 `/help`，確認本人可收到管理回覆，再傳 `/配對`。只有店主能開啟配對；該功能僅在 `BOT_MODE=test` 開放。
5. 店主私下收到五分鐘內有效、難猜的一次性文字「測試配對 <碼>」，只把完整文字私下交給指定的另一位 LINE 使用者，請對方傳給官方帳號。不要公開、貼到本聊天或日誌，也不要拿店主自己當測試客人。
6. 對方送出配對文字後，程式只留下待確認候選：不自動授權、不回覆該人、不呼叫 AI，配對碼與候選原文不進一般事件。店主傳 `/配對狀態`，查看 P 代號與到達時間，**向指定的人核對**後，再傳 `/確認配對 P000001`（換成實際代號）。無法核對時使用 `/取消配對`，不要確認。
7. 確認完成後，請已授權的測試者再送**下一則一般訊息**，驗證實際收到固定回覆，店主實際收到原文初步通知與待辦。AI 理解模式完成後另有同一編號的整理更新；固定模式不抽取時段／項目。檢查通知內時間、客人代號、階段、需求、預約狀態與回覆送達狀態。配對文字本身不會補做一般接待。
8. 由已授權的測試人員驗證未配對身分與群組的限制：一般未知身分不應產生 AI 請求、客人回覆或私人通知內容；群組與多人聊天室不在本版服務範圍。
9. 店主測試 `/pending`、`/take`、`/resume`、`/done` 與回饋。接手期間由測試客人再傳訊，應保存與通知店主，且不自動回答。
10. 重啟 Web Service，確認已配對授權、未結案待辦與接手狀態仍保留；再完成一輪測試。確認 LINE 送出失敗與結果未知的狀態能辨識，避免把未知狀態當成成功。

`/取消配對` 只關閉尚未確認的窗口，不移除已核准測試者。`/移除測試 P000001` 只撤銷該 P 代號的動態配對授權；若同一人也在 `TEST_LINE_USER_IDS` 手動靜態名單，需由本人從 Render 安全環境設定另行移除並套用。撤銷會阻止後續或尚未發出的接待；**已開始的 AI 請求或外送無法撤回**。

窗口與待確認候選在開啟五分鐘後失效，逾期不能確認，候選識別會清除；取消或確認後也會清除候選識別。已關閉窗口的精簡紀錄在 24 小時後清理。核准的動態授權保存在資料庫，重啟後保留至移除；變更 `LINE_CHANNEL_SECRET`（channel 簽章密鑰）或 `OWNER_LINE_USER_ID`（店主識別碼）會隔離舊授權，需要重新配對。店主配對管理的回覆載荷與結果內容會清除，避免配對碼進入持久紀錄。

「測試配對」（後接空白或結尾）是保留的配對語法；含此語法的訊息不進一般客服或 AI，正式模式也不當普通聊天處理。這是避免回傳或保存配對碼的保密設計。

真實 LINE 收發與推播額度、封鎖、channel 設定都會影響結果。店主沒有收到通知時，不要只憑 HTTP 200 就視為成功；檢查私有資料庫的工作／送達狀態與不含內文的操作日誌。通知失敗不應重送客人回覆，結果未知時也不要盲目重發。

## 6. 確認店務知識，再啟用 AI

儲存庫已附 `knowledge/salon.md` 與 `knowledge/facts.json`，初次 `test/fixed` 啟動不需要再人工提供新檔案。啟用 AI 前，由店主審閱 `knowledge/salon.md`，補齊已確認的服務、價格、地址、營業時間、預約規則及去識別化語氣範例。未知項目保持「待確認」。不要加入客人姓名、電話、LINE ID、完整聊天紀錄、API 金鑰或資料庫備份。

同時維護與 `salon.md` 放在同一資料夾的 `facts.json`。這是實際對客人回覆的資料來源：`address` 與 `hours` 填已確認文字、`services` 填 `{"name":"服務名稱","price":"已確認的價格說明"}`；未知值保持 `null`，不要補猜。`faqs` 每筆格式為 `{"keywords":["客人問題關鍵詞"],"answer":"你確認過的回法"}`，關鍵詞至少兩字；避免太廣泛。`voice.greeting` 與 `voice.handoff` 可調整成你的語氣。審閱完才把 `approved` 改為 `true`。未核准時不會使用其中的店務事實；AI 自由生成的回覆不會直接發給客人。沒有對應資料的詢問會留下待辦並轉交本人，之後可持續新增常見問答。

本次雲端環境無法讀取個人網站與公司預約網站；提供連結不表示已驗證網頁內容、供應商或 API。現階段只引導至既有預約網址，沒有平台串接。客人說「我已預約」只記為客人自述，不能自動改成平台已確認。

店務知識確認後，在 Render 安全設定 `SALON_AI_API_KEY` 與帳號確實支援的 `AI_MODEL`，再把 `RESPONSE_MODE` 改成 `ai`，保留 `BOT_MODE=test` 並重新部署。用真人測試客人檢查一般詢問、未知價格、預約需求、已預約自述、要求真人、不支援的圖片／音訊，以及店主接手。AI 失敗或逾時應留下待辦並使用保守的人工確認提示，不得生成精確報價或成功預約。

完成真人端到端驗收、資料告知、備份與回復準備後，才由管理員把 `BOT_MODE` 改為 `live`。這會開放一般一對一客人，請安排店主在場觀察第一輪訊息。保留可快速切回測試模式或停用 webhook 的操作權限。

## 7. 店主日常操作

店主使用設定好的個人 LINE 對此官方帳號傳送指令，不是把指令傳給客人。以下代號是格式範例，請換成實際通知中的編號：

| 指令 | 意思 |
| --- | --- |
| `/help` | 顯示操作說明 |
| `/配對` | 僅測試模式：開啟五分鐘窗口，私下收到一次性測試文字 |
| `/配對狀態` | 查看候選 P 代號、到達時間與已配對代號 |
| `/確認配對 P000001` | 向指定的人核對後，明確加入測試名單 |
| `/取消配對` | 取消尚未確認窗口，不影響既有授權 |
| `/移除測試 P000001` | 撤銷動態配對授權；手動靜態名單需另行移除 |
| `/pending` | 列出待辦與客人代號 |
| `/pending T000001` | 依上一頁最後提供的代號查看較舊待辦 |
| `/take C000001` | 接手該客人；之後新訊息交由店主處理 |
| `/resume C000001` | 明確恢復該客人的自動回覆 |
| `/done T000001` | 將待辦結案 |
| `/confirm T000001` | 店主依自己查證結果，人工確認此預約；不會查詢平台 |
| `/feedback T000001 這次應先詢問髮況，再由我報價` | 記錄問題及正確回法 |

從 LINE Official Account Manager 手動回覆客人前，先 `/take`；程式不保證能偵測所有後台手動訊息。處理完再依需要 `/done` 與 `/resume`。完成待辦與恢復自動回覆是分別操作，避免結案後意外開始自動回覆。

人工接手期間的新文字訊息，在 AI 理解模式仍整理客人補充或更改的需求並通知店主，但不發送客人回覆；固定模式只通知原文。店主恢復後，人工接手時已收到或已開始處理的舊訊息仍保持不自動回覆，新訊息才依當前狀態處理。接手／恢復決策有版本保護，AI 晚完成不會改回舊狀態；已在接手前送出的網路請求無法收回。

客人要求真人，或涉及複雜染燙、髮況判斷、未確認報價、客訴與退款時交給店主。`/confirm` 是店主的確認紀錄，不能當成平台 API 驗證。不要為了測試而確認不存在的正式訂單。

## 8. 更新、保存與回復

回饋先留在私人資料庫，AI 不會自動永久學會。由店主與建置者把可泛用的正確回法整理、去識別化後，再更新店務指南或程式規則。每次更新先執行：

```bash
npm ci
npm run check
npm test
npm run build
```

審閱 Git 差異，確認沒有密鑰與客人資料。記錄部署 commit，在測試模式驗證改動後才部署正式版本。資料庫變更先備份並檢查與前一版程式的相容性；不要假設回復程式版本會回復資料。

原始對話、含原文回饋與通知載荷採 30 天清理；已結案待辦的精簡資料與事件去重識別碼採 90 天。未結案待辦保留必要狀態，超期原文仍應清除。備份的保留期由資料庫方案另行管理，刪除線上資料不等於所有備份立即刪除。正式使用前確認告知方式、資料存取人員、備份保存期與還原流程。

通知第一次失敗後約 30 秒再試，第二次失敗後約 2 分鐘再試，最多三次並沿用相同重試識別碼。操作日誌的 `owner_notification_failed` 只包含通知識別碼、次數、送達狀態及是否終止，不含對話或憑證；即使通知失敗，待辦仍保存在資料庫，店主可用 `/pending` 查詢。人工指令與客人 AI 工作有獨立的處理流程，所以 `/take` 不必等待正在生成的 AI 回覆。

初步原文與 AI 整理使用獨立通知階段，每階段只有一列工作與固定重試識別碼；LINE 重送事件不建立第二份通知。每則最多有初步與更新兩種推播，會分別使用訊息額度。AI、客人回覆或通知失敗不會互相阻斷；時段仍只是客人需求。來源時間較早、或已被新訊息接續的整理會被抑制，原文通知及其訊息時間仍保留。推播實際送達仍受 LINE 的額度、封鎖與網路狀態影響。

出現錯誤回覆時，先用 `/take` 接手相關客人，必要時切回 `BOT_MODE=test` 或停用 LINE webhook，並恢復原有人工客服。Render 可重新部署上一個已驗證的 commit；回復後重新檢查健康狀態、固定回覆、店主通知與接手狀態。涉及不相容 migration 時，由有權限的維護者依備份／相容性計畫處理，切勿直接刪表或覆蓋正式資料。

## 9. 常見問題

| 現象 | 先檢查 |
| --- | --- |
| 程式拒絕啟動 | 四個必填環境變數、`BOT_MODE`／`RESPONSE_MODE`；測試名單可空，若手動填入則不可包含店主；修改後重啟 |
| LINE Verify 失敗 | HTTPS 網域、`/webhook` 路徑、服務健康、channel secret 是否屬於同一 channel；簽章需要原始 body |
| 存活但未就緒 | `DATABASE_URL`、migration、資料庫存取與 TLS；不要停用驗證 |
| 測試客人沒有回覆 | 店主是否已確認配對或安全填入手動名單、是否為確認後的一般訊息、人工接手狀態、是否一對一、LINE token／額度及送達狀態；配對文字本身不回客人 |
| 配對沒有成功 | 是否仍在 test 模式及五分鐘內、是否由另一人傳正確一次性文字、店主是否核對 P 代號並明確確認；過期／取消後重新 `/配對` |
| 店主沒有通知 | 店主是否加好友、ID 與 channel 範圍是否正確、是否封鎖、推播額度、通知工作的失敗／未知狀態 |
| AI 未啟用 | 知識是否已確認、`RESPONSE_MODE=ai`、金鑰與模型權限；固定模式不會呼叫 AI |
| 重啟後 demo／正式資料不見 | 是否用了不同資料目錄或不同資料庫；正式服務不可使用 `.local/demo` |

## 10. 啟動失敗的安全診斷

`732a51f` 的啟動錯誤只顯示通用中文訊息，無法據此分辨設定、知識檔、TLS、DNS 或資料庫認證。診斷版 `3a375bb` 已上傳並由本人部署；日誌曾回報 `database_migration / DEPTH_ZERO_SELF_SIGNED_CERT`，本人更換 External URL 後回報就緒及首則收發成功。未來若啟動失敗，可讀一行 `event: "startup_failed"` 的 JSON。

該紀錄只含固定的 `stage`（啟動階段）、白名單 `code`（安全錯誤分類），必要時加上 `fields`（有問題的設定名稱）。不含設定值、URL、連線字串、原始錯誤訊息、stack、cause 或外部服務內容。提供這一行即可協助定位，仍不要貼環境設定頁或完整連線字串。

階段分為 `environment`（載入本機環境檔）、`configuration`（檢查設定）、`knowledge`（讀指南）、`facts`（讀取與檢查店務事實）、`database_configuration`（檢查資料庫 URL／TLS 選項）、`database_migration`（連線並更新資料結構）、`clients`（建立外部服務客戶端）、`runtime`（初始化資料庫工作並監聽）。其中 `database_migration` 也包含取得資料庫連線；不能只憑這個階段就認定是 SQL 更新出錯。

| 安全代碼 | 可以確認的範圍 |
| --- | --- |
| `CONFIG_MISSING`／`CONFIG_INVALID` | 先檢查 `fields` 列出的必要欄位或格式；只核對名稱，不傳設定值 |
| `DB_URL_INVALID`／`DB_TLS_POLICY_INVALID` | 資料庫網址格式或 TLS 選項在連線前被拒絕；不代表資料庫已被連上 |
| `ENOENT`／`EACCES` | 配合階段辨識本地啟動檔案不存在或無權讀取，不輸出檔案原文 |
| `FACTS_JSON_INVALID`／`FACTS_SCHEMA_INVALID` | 店務 facts 檔案的 JSON 或結構不符合格式 |
| `ENOTFOUND`／`EAI_AGAIN` | 資料庫等網路主機名稱解析失敗；不輸出實際主機名 |
| `ERR_TLS_CERT_ALTNAME_INVALID` 等允許的 TLS 代碼 | 憑證或主機名稱驗證失敗，依分類查核；不可停用驗證 |
| `28P01`／`28000` | 資料庫認證被拒絕；不要貼帳號、密碼或完整 URL |
| `EADDRINUSE`／`EACCES` | 配合 runtime 階段查核監聽連接埠或存取權限 |
| `UNKNOWN` | 沒有可安全採用的已知分類；仍不能猜測根因，也不會輸出原始例外 |

建置成功不等於服務已啟動；`event: "started"` 表示主程式已完成其啟動流程，仍需驗證 `/readyz`。即使 `/readyz` 成功，也不代表 LINE 憑證、真實收發或手機通知已驗收。
